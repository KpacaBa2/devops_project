## 2. Backlog задач (P0 / P1 / P2)

### P0 — Обязательный минимум (MVP и сдача обязательного сценария)
- **[P0-1]** Модуль криптографии `CPV1` в браузере (`PBKDF2-SHA256` 600k + `AES-256-GCM` с `AAD = "CPV1\x01"`).
- **[P0-2]** Инициализация хранилища (`vault-meta.json`), генерация `DEK`, экспорт секрета восстановления (Recovery Key / пароль).
- **[P0-3]** Два адаптера хранилища на фронтенде: `GoogleDriveStorageAdapter` (реальный Drive API со scope `drive.file`) и `SandboxStorageAdapter` (REST в `api` для автотестов).
- **[P0-4]** Серверная валидация в `api`: эндпоинт `/api/sandbox/objects` принимает только файлы с заголовком `CPV1\x01` и возвращает `400 Bad Request` при попытке загрузить открытый JPEG (`FF D8 FF`) или PNG (`89 50 4E 47`).
- **[P0-5]** Обязательный пользовательский сценарий в UI: Вход -> Создание/разблокировка хранилища -> Загрузка фото (до 5 МБ) -> Просмотр галереи с расшифровкой -> Очистка браузера -> Восстановление по сохраненному секрету.
- **[P0-6]** Docker Compose из 3 контейнеров (`proxy` Caddy с HTTPS/CSP, `web`, `api`) с `healthcheck` у каждого сервиса.
- **[P0-7]** CI/CD в GitHub Actions: lint + unit-тесты + сборка Docker-образов + smoke-тест стека (включая негативный и позитивный тест на отсутствие открытого JPEG).

### P1 — Важные улучшения для высокой оценки по DevOps
- **[P1-1]** Автоматический деплой на облачный VPS по push в `main` (через SSH / Docker Compose pull & up) с автоматическим получением Let's Encrypt сертификата в Caddy.
- **[P1-2]** Структурированные JSON-логи в `api` и `proxy` (без логирования токенов, ключей и имен файлов) + скрипт просмотра логов.
- **[P1-3]** Генерация зашифрованных миниатюр (thumbnails до 200px через `<canvas>` в браузере) и хранение их внутри `manifest.enc` для быстрой отрисовки галереи.
- **[P1-4]** Сканирование уязвимостей Docker-образов (например, Trivy в GitHub Actions) и запуск контейнеров от непривилегированного пользователя (`non-root`).

### P2 — Дополнительные опции (только если останется время на 7–8 неделе)
- **[P2-1]** Удаление фото из галереи и синхронное удаление `blob_<uuid>.enc` из Google Drive.
- **[P2-2]** Смена пароля хранилища (перешифровка только `wrappedKey` в `vault-meta.json` без перезаливки фотографий — преимущество схемы с `DEK`/`KEK`).
- **[P2-3]** Простой мониторинг состояния контейнеров и места на диске VPS.

## 3. Список обязательных автотестов

1. **Unit-тест 1 (Шифрование и формат `CPV1`):**
   * На вход подается буфер с сигнатурой JPEG (`FF D8 FF E0 ...`). На выходе проверяется, что первые 5 байт равны `43 50 56 31 01` (`CPV1\x01`), длина увеличилась ровно на 33 байта, а последовательность `FF D8 FF` в начале отсутствует.
2. **Unit-тест 2 (Уникальность Nonce/IV):**
   * Двукратное шифрование одного и того же фото одним и тем же ключом `DEK` дает разные байты `IV` (смещение `5..16`) и разный шифротекст.
3. **Unit-тест 3 (Проверка целостности AAD и Auth Tag):**
   * Изменение байта версии в заголовке (`0x01` -> `0x02`) или любого байта шифротекста приводит к гарантированному выбросу ошибки в `decryptCpv1`.
4. **Unit-тест 4 (Восстановление `DEK` из пароля и `vault-meta.json`):**
   * Проверка цикла `deriveKek` -> `wrapDek` -> очистка памяти -> `unwrapDek` с верным паролем (успех) и с неверным паролем (ошибка).
5. **Интеграционный / Главный тест безопасности (Отсутствие открытого JPEG в запросе к хранилищу):**
   * Перехват исходящего payload из фронтенда / отправка в `/api/sandbox/objects`:
     * Позитивный кейс: отправка зашифрованного `CPV1` блоба возвращает `201 Created`, первые байты сохраненного объекта — `CPV1\x01`.
     * Негативный кейс: попытка отправить открытый JPEG (`FF D8 FF`) отвергается сервером с кодом `400 Bad Request` (`PLAINTEXT_IMAGE_REJECTED`).
6. **Smoke-тест Docker Compose в CI:**
   * Поднятие `docker compose up -d --wait`, проверка `/api/health` через `proxy`, прогон e2e/smoke-скрипта загрузки и скачивания зашифрованного объекта.
