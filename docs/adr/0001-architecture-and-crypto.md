# ADR-0001: Архитектура E2EE-галереи, OAuth Code Flow и два адаптера хранилища

* **Статус:** Принято
* **Дата:** 2026-10-21
* **Контекст:** Курсовой проект по DevOps (команда 3 человека, 8 недель). Темы кафедры №35 («Развертывание и управление контейнеризированным веб-приложением в облачной среде») и №5 («Многоконтейнерная система на Docker Compose»).

## 1. Принятые архитектурные решения

1. **Клиентское шифрование (Client-Side Encryption в браузере):**
   * Фотографии, миниатюры и метаданные (имена файлов, даты) шифруются в браузере через стандартный `Web Crypto API` (`PBKDF2-HMAC-SHA256` 600 000 итераций + `AES-256-GCM`) до отправки в сеть.
   * Сервер приложения (`api`) никогда не получает открытые фотографии, пароль пользователя, `KEK` или `DEK`.

2. **Точная формулировка модели доверия (вместо «100% Zero-Knowledge»):**
   * Система обеспечивает **клиентское шифрование данных перед отправкой в облачное хранилище при условии целостности клиентского кода (Trust-On-First-Use / честный сервер раздачи статики)**.
   * См. раздел «Что может владелец сервера» ниже.

3. **Состав Docker Compose стека (3 контейнера):**
   * `proxy` (Caddy 2) — терминация HTTPS (обязателен для работы `window.crypto.subtle`), заголовки безопасности (`CSP`, `HSTS`, `X-Content-Type-Options`), маршрутизация `/` -> `web` и `/api/*` -> `api`.
   * `web` (Nginx + статический фронтенд) — отдает JS/HTML-приложение, выполняющее криптографию и работу со `StorageAdapter`.
   * `api` (Backend-сервис) — выполняет:
     1. Обмен OAuth `authorization code` на токены и обновление `access_token` по `refresh_token`.
     2. Выдачу публичной конфигурации (`/api/config`) и проверку здоровья (`/api/health`).
     3. Простой REST-эндпоинт песочницы (`/api/sandbox/objects`) для `SandboxStorageAdapter` (используется в CI/CD и при локальной проверке без Google), который **проверяет заголовок `CPV1\x01` и отвергает открытый JPEG (`FF D8 FF`)**.

4. **Два адаптера хранилища на фронтенде (`StorageAdapter`):**
   * Мы **не эмулируем** сложный протокол Google Drive API внутри нашего `api`.
   * Вместо этого фронтенд использует единый интерфейс `StorageAdapter` с двумя реализациями:
     * `GoogleDriveStorageAdapter` — в продакшене ходит напрямую из браузера в `https://www.googleapis.com/...` со заголовком `Authorization: Bearer <access_token>`.
     * `SandboxStorageAdapter` — в CI/CD и локальных автотестах ходит по простому REST в `/api/sandbox/objects`.

## 2. Пошаговый токен-поток (OAuth 2.0 Code Flow), Cookie и защита от CSRF

1. **Шаг 1 (Инициация входа в браузере):**
   * Пользователь нажимает «Войти через Google». Браузер вызывает `google.accounts.oauth2.initCodeClient` (`ux_mode: 'popup'`, `scope: 'https://www.googleapis.com/auth/drive.file'`).
2. **Шаг 2 (Отправка одноразового кода на Backend):**
   * Браузер получает короткоживущий `code` и отправляет `POST /api/auth/google/callback` с заголовком `Content-Type: application/json` и `X-Requested-With: CPV1-Client`.
3. **Шаг 3 (Обмен кода и хранение `refresh_token`):**
   * `api` обращается к `https://oauth2.googleapis.com/token`, используя серверный `GOOGLE_CLIENT_SECRET`, и получает `access_token` (живет 3600 с) и `refresh_token`.
   * **Где хранится `refresh_token`:** Чтобы не поднимать отдельную СУБД ради одного поля, `api` упаковывает `refresh_token` в зашифрованную серверным ключом (`SESSION_SECRET`, AES-256-GCM) куку `cpv1_rt` со строгими флагами:
     * `HttpOnly` (недоступна из JavaScript при XSS);
     * `Secure` (передается только по HTTPS);
     * `SameSite=Strict` (не отправляется при переходах с чужих сайтов);
     * `Path=/api/auth` (отправляется браузером **только** на эндпоинты обновления/выхода, а не на каждый запрос).
4. **Шаг 4 (Как браузер получает и использует `access_token`):**
   * В ответ на `/api/auth/google/callback` (и при последующих вызовах `POST /api/auth/refresh`) `api` возвращает JSON `{ accessToken, expiresIn }`.
   * Браузер хранит `accessToken` **только в оперативной памяти вкладки (JS-переменная)** — ни в `localStorage`, ни в `sessionStorage`.
   * За 2 минуты до истечения `expiresIn` (или после перезагрузки страницы F5) браузер вызывает `POST /api/auth/refresh`, браузер автоматически прикладывает `HttpOnly` куку `cpv1_rt`, и `api` выдает новый `accessToken` в память вкладки.
5. **Шаг 5 (Защита от CSRF):**
   * Комбинация из трех барьеров на эндпоинтах `/api/auth/*`:
     1. Флаг `SameSite=Strict` у куки `cpv1_rt`.
     2. Обязательная проверка заголовка `Origin` на совпадение с `APP_ORIGIN` (`https://ваш-домен`).
     3. Обязательное наличие кастомного заголовка `X-Requested-With: CPV1-Client` (простая HTML-форма с чужого сайта не может отправить кастомный заголовок без CORS-preflight, который сервер заблокирует).

## 3. Что может владелец сервера (ограничения веб-криптографии)

Поскольку JavaScript-код при каждом открытии страницы загружается с нашего сервера (`web` за `proxy`), важно честно понимать границы модели безопасности:

* **Честный сервер (наша цель в проекте):** Сервер отдает неизмененный JS-бандл. Пароль, `KEK`, `DEK` и открытые фото никогда не покидают память браузера. При взломе хранилища Google Drive или перехвате логов `api` злоумышленник видит только зашифрованные блобы `CPV1`.
* **Если скомпрометирован сам сервер раздачи статики (`web` / `proxy`):**
  * **Подмена JS-кода:** Владелец сервера (или атакующий, получивший root на VPS) технически может подменить `index.js` на версию, которая перехватывает вводимый пароль или `DEK` и отправляет его в сеть. Это фундаментальное свойство любого веб-приложения без браузерного расширения.
  * **Как мы снижаем риск (DevOps-меры):**
    1. Строгий заголовок **CSP (`Content-Security-Policy`)** на `proxy`: разрешает `connect-src` (отправку сетевых запросов) **только** на `self` и `https://www.googleapis.com` / `https://accounts.google.com`. Даже если в код попадет сторонняя XSS-уязвимость, браузер заблокирует отправку ключа на чужой домен.
    2. **Subresource Integrity (SRI)** и неизменяемые Docker-образы, собираемые в публичном GitHub Actions из проверяемого исходного кода.
